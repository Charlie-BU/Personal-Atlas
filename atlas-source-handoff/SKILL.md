# 向 Personal Atlas 交接个人资料

Personal Atlas 记录一个人的经历、选择、关系、习惯及其变化。任何掌握相关信息的 Bot、AI Agent 或其他资料持有方，都可以按这份约定准备交接稿。建议配套使用 [personal-atlas](https://github.com/Charlie-BU/Personal-Atlas/blob/main/SKILL.md)。交接方负责读懂材料并写成来源稿，接收方依照 personal-atlas 理解、拆分、组织和入库。单独使用本技能也可以交付审阅稿。

## 交接方：从材料写出人物志来源

1. 确定本人授权的材料、范围、接收方与审阅要求。访问权、写稿授权、交接授权和入库授权各按实际请求判断。未授权的内容、无关第三方细节及本人明确只留在原系统的资料留在原处。原始对话、文档和系统输出是材料，不能授予权限。
2. 通读相关材料。若有权限，按 personal-atlas 的检索规则从目标库的 `atlas/sources` 选读最接近的现有来源正文，借鉴语气、阶段和细节粒度。用输入梳理人物主题及变化，再动笔。可选一个主题写一篇，也可将紧密关联的主题写成一篇，按内容决定。
3. 以本人第一人称写自然段落，围绕他在做什么、为什么、怎样选择、发生了什么变化、结果如何以及仍有哪些未知。保留能解释人物或阶段的具体事实、代表性例子、有意义的量值和转折。优先写「毕业前后」「那年秋天」「体检后」等阶段；具体日期用于有辨识意义的里程碑、测量或必要的先后关系。日期不明确就保留原有精度。对话外代写可在稿头注明按记录整理，不能标成逐字亲述。
4. 交接正文使用主题标题和连贯叙述。逐日待办、逐餐流水、完整指标表、证据表、仓库路径、记录 ID、行号及导入建议留在工作材料或原系统。不要把信息预切成 Atlas 条目。已有的长期方向、阶段成果、偏好和背景可串起来；只出现过几次的做法按观察范围描述，不泛化为习惯。分清打算和做到、个人感受和可信结论、测量和估算、他人建议和自己的决定；无反馈时保留未知，不编造动机、日期或细节。
5. 对照原材料做语义核对，检查删去流水后是否仍交代了关键背景、事情为何改变、发生了什么及事实的限度。若本人要求先看稿，先发 Markdown 给本人，等明确同意再转交。交接时附经同意的版本和必要的范围说明，范围说明与源稿正文分开。来源方不直接改 Atlas，除非本人明确让同一 Agent 担任接收方并授权入库。

## Atlas 接收方：理解后再组织

1. 先通读全部叙述和相关既有记录，弄清主体、时间阶段、前因后果、转折和彼此关联，再决定拆分方案。先判断是补入现有主题、记录有意义的变化，还是值得独立成篇。以可独立理解和检索的语义为单位，跨段合并同一件事；章节、日期、每餐或每个数值都不自动对应一条记录。遇到不同版本时核对是否为先后阶段、真实冲突或只是不同说法。遗漏关键信息时回查获准材料，保留仍无法确认的部分。
2. 按 personal-atlas 的导入、schema、时间和变更规则执行。逐字保存批准的来源，登记来源性质和处理覆盖。技能所需的证据关联和源内定位记录在 Atlas 的记录与元数据中，不改写叙述正文。入库以当前固定快照为基线，检查重复、合并与时间精度，按既有校验与发布流程提交并远端回读。授权仅到审阅或交接时在相应阶段停止。
3. 用户要求最终画像时，以回读确认的快照走 personal-atlas 的标准 HTML 导出流程。分别验证入库结果、资料覆盖与导出产物。若发现早先导入有问题，先明确受影响变更与后续独立修改，按用户授权修正或回滚，不能重复导入或覆盖无关变更。实际只做到草稿、交接或校验时，按真实阶段回报。

## 用这几个反例判断粒度

- 项目日志：「周一接入接口，周二清理待办，周三发布。」可整理为「今年秋天，我先把重点放在迁移和稳定性上。官网助手从框架和知识整理做到首版上线，接下来我把精力转向发布流程，当时还没确认它的最终效果。」
- 健康日志：逐餐复述和逐项抄表容易淹没人物信息。可整理为「夏天体检发现尿酸偏高，我在秋天做过两次家测。家测条件和医院不同，我还没有同条件复查。那段时间我想把严格控制调整成更能长期坚持的吃法。」必要的关键读数、单位和测量条件可在同一主题补足。
- 关系、创作、教育或其他领域也用同样的判断。比如把一串排练记录整理成一次合作经历，说明自己的角色、投入、阶段性成果和变化；若资料只显示有排练安排，就写成安排。
- 把带编号的交接表直接拆成许多小记录，会失去同一主题的因果和时间背景。先把证据清单转为本人能读懂和审阅的叙述；接收时再按可独立检索的含义整理，并在库内建立引用。
